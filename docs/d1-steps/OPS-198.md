- **Copy rehearsal: a throwaway Postgres built from the migrations, and the copy run from it (OPS-198, step 8b3a of OPS-93).** Staging shares production's Postgres, so a copy *into* Postgres (the way back after the cutover, step 8b3b) could only be tried on production. This step builds the place to try it first, and proves a second thing on the way: all 58 Postgres migrations replay on an empty database. The CI job **Copy rehearsal** (`copy-rehearsal` in `.github/workflows/ci.yml`) starts `postgres:15` as a service, then: `scripts/d1-copy/rehearsal/apply.mjs` runs `supabase-stubs.sql` and every migration of `src/db/migrations` in the order of `meta/_journal.json`, each in its own transaction, and prints `migrations applied: 58`; `fixture.sql` loads made-up rows with every trigger on (a user made by the `auth.users` trigger, a member, quote, trip and invoice with their generated codes, a blog post, an API key, two `api_requests` rows through the identity column, an audit row); then `scripts/d1-copy/copy.mjs --target staging --mode rehearse` reads that Postgres in one snapshot, loads it into an in-memory D1 (`node:sqlite` with the repo's own D1 migrations, the same INSERTs the remote load runs) and reads counts and key checksums back with the same code the real copy uses, ending `N tables (…), 0 with a difference`. It exits 1 on any difference, and when a table the fixture must fill is empty (so a pass is never a pass over nothing).
- **What the stubs are.** Only what makes the migrations apply, each commented with the migration that needs it: the roles `anon`, `authenticated`, `service_role`, `supabase_auth_admin` and `postgres` (no login), schema `auth` with `auth.users` (id, email, encrypted_password, banned_until, raw_user_meta_data, timestamps), `auth.uid()` and `auth.jwt()` returning null, schema `storage` with `storage.buckets`, and `pgcrypto` (0042 uses `gen_random_bytes`). Real Supabase has far more; none of it is needed to replay the repo's own SQL.
- **Touches nothing live, and cannot.** No secret is used. `apply.mjs` and the rehearsal mode refuse any `DATABASE_URL` whose host is not `localhost` or `127.0.0.1` before they connect (`rehearsal/local.mjs`), the mode refuses any target but `staging`, and no refusal or failure prints the URL, a row value or the server's message (a file name and an error code only). `scripts/d1-copy/rehearsal/local.test.mjs` tests these refusals, with no database, as the first step of the job.
- **Assumption, not verified: Postgres 15.** No run can read the Postgres major version of JetNine's Supabase project (it needs the database). `postgres:15` is the major Supabase gave new projects through 2025. The production preflight of the reverse-copy row (8b3b) prints `select version()` so this is checked where it can be. If the live major differs, change the image tag in the job.
- **Not covered here.** Row level security policies and grants replay (they are in the migrations) but nothing is asserted about them, and the stubs' `auth.uid()` is always null. Password hashes and bans stay out of the staging-shaped rehearsal as they do on staging (`HELD_BACK`); the production target that carries them is OPS-197.
- **Way back.** Revert the merge commit: the job, the rehearsal folder and the `--mode rehearse` branch of `copy.mjs` go; the copy to staging is as before (`--target staging`, `--check` and `--list` are unchanged).
- **Run it locally.** With any local Postgres 15 or newer: create an empty database, `DATABASE_URL=postgresql://USER:PASS@127.0.0.1:PORT/DB`, then `node scripts/d1-copy/rehearsal/apply.mjs`, `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 --single-transaction -f scripts/d1-copy/rehearsal/fixture.sql`, `pnpm exec tsx scripts/d1-copy/copy.mjs --target staging --mode rehearse`. `apply.mjs` refuses a database that already has tables in `public`: drop and recreate it to run again.
