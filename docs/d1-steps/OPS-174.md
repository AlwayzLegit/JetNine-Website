- **Converted to D1: sign-in, emailed links, user and staff writes, OPS-174.** The site's own sign-in sessions (`src/lib/session`), the password check and the password change, the emailed links for sign-in, reset and invite (`src/lib/auth-tokens`), the user helpers (`src/lib/auth-users.ts`: find or create a user for an invite, the guarded role change, "has a password"), the staff row writes in `src/domain/team/commands.ts`, the profile patch in `src/domain/clients/commands.ts` and the sign-in health probe (`checkSignin` in `src/lib/health.ts`) go through `src/lib/identity-store/store.ts` (a Postgres adapter, today's queries moved as they were, and a D1 adapter, one chosen per request by `dbTarget()`); production stays on Postgres. D1 has no `auth` schema, so on D1: (1) the password hash is `user_credentials` only (the older bcrypt hash in `auth.users` does not exist there), and real hashes are never copied to staging, so staging has no password that works until one is set there with a reset or invite link; (2) a ban is `users.banned_until` (migration 0009, D1 only, nullable; on Postgres it stays `auth.users.banned_until`, read in place), and a user with a ban in the future gets no hash and cannot spend a link; the parity test names this one column as a D1-only exception; (3) the role-immutability trigger is gone, so the role change is checked in the app (`roleChangeAllowed`) and written as a compare-and-set on the role that was read, with one re-read and then a refusal if the role moved in between; (4) `consumeToken` is still one `update ... returning` statement (unused, unexpired, right purpose, user not banned), so two clicks together give one winner. The health probe reads the sessions table, the links table and, on D1, `user_credentials` (it has to be readable on staging, and must hold a row once D1 is production). Staging-only effects: the staff and clients lookups that are not writes (the team list, member lists) still read Postgres until their own steps move, so on staging a new invite makes the user row in D1 while the team page still lists Postgres people.
